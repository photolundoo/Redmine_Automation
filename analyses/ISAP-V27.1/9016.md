## 1. Étude du sujet

Le ticket décrit une erreur HTTP 500 lors de la connexion à l'API lorsque le mot de passe du compte contient le caractère « : ». La procédure de reproduction ajoutée au ticket crée un compte avec ce caractère et appelle `POST /api/connect/login`. Après correction, un compte sans droits API reçoit une réponse HTTP 403 avec une erreur explicite de droits insuffisants ; avant correction, l'API retournait HTTP 500. Le ticket est résolu.

## 2. Compte rendu de la situation

**Tenants.** Un caractère deux-points dans le mot de passe ne doit pas faire échouer le traitement HTTP par une erreur serveur interne.

**Aboutissants.** Le plan 13 vérifie déjà la connexion à SmartShieldWebAPI. Il ne couvre pas ce caractère particulier ni la distinction entre authentification et autorisation.

**Objectifs du test.** Vérifier qu'un compte dont le mot de passe contient « : » peut envoyer une requête de connexion sans provoquer HTTP 500 ; selon ses droits, l'API répond avec un résultat d'authentification ou une erreur explicite de droits insuffisants.

## 3. Comparaison avec l'existant

**Recherche dans les plans.** La recherche de `#9016` dans les plans ne retourne aucune étape. Le plan 13, section « SmartShieldWebAPI », vérifie que la connexion à l'API est possible avec un compte valide, sans scénario de mot de passe contenant le caractère deux-points.

**Comparaison des procédures.** Le scénario s'intègre à la vérification de connexion existante de SmartShieldWebAPI. Il complète le contrôle d'un compte valide par un compte avec le caractère concerné et distingue le refus normal d'autorisation d'une erreur 500.

**Issue retenue.** Issue B — Adapter l'existant : compléter la section « SmartShieldWebAPI » du plan 13 par le test de connexion avec un mot de passe contenant « : ».

## 4. Procédure de test proposée

**Écarts avec la procédure existante.** Conserver le contrôle de connexion avec un compte valide. Ajouter les essais avec des comptes de test dont le mot de passe contient « : », avec et sans droits API.

**Connexion à SmartShieldWebAPI avec un mot de passe contenant « : »**
- Créer ou sélectionner deux comptes de test dont le mot de passe contient le caractère « : » : un compte autorisé à utiliser l'API et un compte sans droits API. Résultat attendu : les deux comptes sont disponibles pour le test et aucune donnée d'authentification réelle n'est inscrite dans les résultats. (#9016)
- Envoyer une requête `POST /api/connect/login` avec les identifiants du compte autorisé. Résultat attendu : l'API ne retourne pas HTTP 500 et établit la connexion selon le contrat d'authentification. (#9016)
- Envoyer la même requête avec le compte sans droits API. Résultat attendu : l'API ne retourne pas HTTP 500 et répond par un refus explicite lié aux droits, notamment HTTP 403 comme indiqué dans le ticket. (#9016)
- Consulter les journaux SmartShieldWebAPI après les deux requêtes. Résultat attendu : aucune exception serveur fatale ni erreur de traitement liée au caractère deux-points n'est enregistrée. (#9016)

### Prérequis et moyens

- Utiliser uniquement des comptes et mots de passe de test sur une instance isolée.
- Transmettre les identifiants par un mécanisme de saisie sécurisé ; ne pas les recopier dans l'analyse, les journaux de campagne ou une capture d'écran.
- Si le contrat d'authentification renvoie un code de succès différent, constater la réponse conforme au contrat ; le critère bloquant de ce ticket est l'absence d'erreur HTTP 500.

## 5. Intégration proposée

Dans le plan 13, compléter la section **SmartShieldWebAPI**, au niveau du contrôle de connexion à l'API, par un scénario de connexion avec un mot de passe contenant « : » et des droits API différents.
