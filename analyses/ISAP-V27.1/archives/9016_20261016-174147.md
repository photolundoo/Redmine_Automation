## 1. Étude du sujet

Une authentification API avec un mot de passe contenant un deux-points retournait HTTP 500. La correction doit laisser l’API retourner le statut fonctionnel attendu, par exemple 403 si le compte manque de droits.

## 2. Compte rendu de la situation

**Tenants.** Le découpage des identifiants d’authentification ne gérait pas un deux-points dans le mot de passe.

**Aboutissants.** Le défaut interne ne doit plus exposer une erreur HTTP 500.

**Objectifs du test.** Vérifier qu’un compte de test avec caractère spécial obtient un statut applicatif, non une erreur serveur.

## 3. Comparaison avec l'existant

**Recherche dans les plans.** La recherche de #9016 dans le plan 13 ne retourne aucune étape. La fiche **SmartShieldWebAPI** couvre les appels API, sans authentification avec caractère spécial.

La procédure complète cette fiche.

## 4. Procédure de test proposée

**Authentification API avec deux-points**
- Créer ou utiliser un compte API de test dont le mot de passe contient un deux-points, sans inscrire sa valeur dans le plan. Résultat attendu : le compte est disponible pour le test. (#9016)
- Appeler l’API avec ce compte. Résultat attendu : la réponse est fonctionnelle, telle que succès ou refus de droits, et n’est jamais HTTP 500. (#9016)

## 5. Intégration proposée

Ajouter ces étapes à **SmartShieldWebAPI** du plan 13 Outils externes, parmi les contrôles d’authentification.
