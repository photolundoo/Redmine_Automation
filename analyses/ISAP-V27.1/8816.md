## 1. Étude du sujet

Le ticket demande un ensemble de tests officiels visant à vérifier la conformité du plugin CSR au standard DC-09, à partir de l’annexe C. L’historique fournit une matrice de tests pour les protocoles pris en charge, le chiffrement, les CRC, les numéros de séquence, les données d’identification, la supervision et les réponses du récepteur. Plusieurs cas sont indiqués comme déjà validés, un cas de supervision de 24 heures reste à tester et le support de la réponse RSP est indiqué comme non implémenté.

## 2. Compte rendu de la situation

**Tenants.** L’historique précise l’usage du simulateur PE, de la démo ACME et du plugin SIA CSR. Il précise aussi que le sous-ensemble DC-03 n’est pas exploitable en l’état ; le périmètre de ce ticket a été recentré sur DC-09.

**Aboutissants.** La matrice d’essais a été ajoutée à l’historique du ticket, lequel est résolu. Elle n’est pas présente comme fiche de validation dans les plans consultés. Le ticket ne fournit pas de décision établissant son emplacement dans le plan de validation du projet.

**Objectifs du test.** Transformer les cas DC-09 pertinents de la matrice en procédure exécutable et distinguer les comportements conformes, les tests restant à réaliser et les fonctionnalités non implémentées.

## 3. Comparaison avec l'existant

**Recherche dans les plans.** `#8816`, « DC-09 », « CSR » et « SIA » : aucun résultat correspondant dans les plans 06 et 08. Le plan 06 contient `INT03 — Tests avec simulateur`, mais cette fiche concerne `IntrusionProcessor` et `intrusion_simulator`, pas le CSR. La correspondance oriente « ISAP Plugins - Détection Intrusion » vers le plan 06 et les fiches INT01/INT03.

**Comparaison des procédures.** INT03 vérifie le fonctionnement de l’IntrusionProcessor à l’aide d’un simulateur d’intrusion ; elle ne reprend aucun test de conformité DC-09 de la matrice du ticket. Le contenu détaillé du ticket justifie une procédure spécifique au CSR plutôt que l’ajout de cas dans INT03.

**Issue retenue.** D, car le plan ne contient pas de procédure DC-09 et la matrice du ticket requiert une fiche dédiée.

## 4. Procédure de test proposée

**Écarts avec la procédure existante.** Nouvelle procédure de conformité CSR ; ne pas réutiliser les cas INT03. Exécuter les tests avec des données et clés de test temporaires, sans recopier d’identifiants ou de secrets du ticket.

**Conformité DC-09 avec le simulateur PE**
- Vérifier dans la documentation du plugin les protocoles TCP/UDP pris en charge et configurer le simulateur pour chaque mode annoncé. Envoyer un message. Résultat attendu : une réponse est reçue sans erreur dans le journal. (#8816)
- Configurer une clé de test identique dans le simulateur et le CSR. Envoyer un message chiffré ; répéter avec une clé différente et pour les tailles prises en charge par la matrice. Résultat attendu : le message chiffré avec la clé identique crée un événement, celui avec une clé différente est refusé et les tailles acceptées sont traitées. (#8816)
- Envoyer un message chiffré contenant plusieurs blocs et un message avec un CRC incorrect. Résultat attendu : le message valide est traité et le message au CRC erroné ne reçoit pas de réponse. (#8816)
- Envoyer des messages non chiffrés avec les formats d’identification SIA-DCS et ADM-CID. Résultat attendu : le récepteur répond et crée l’événement attendu. (#8816)
- Envoyer des messages avec numéros de séquence répétés, puis la séquence de passage de 9998 à 0002 décrite dans la matrice. Résultat attendu : un message répété ne crée pas de nouvel événement et les messages suivants sont traités. (#8816)
- Exécuter les cas d’identification du récepteur, de préfixe et de compte avec des valeurs de test limites issues de la matrice. Résultat attendu : les messages sont acquittés et les objets créés sont associés à des centrales distinctes lorsque les préfixes ou comptes diffèrent. (#8816)
- Configurer la supervision pour envoyer un message toutes les 50 secondes et l’exiger toutes les 60 secondes. Laisser le test tourner 24 heures, puis couper la supervision. Résultat attendu : aucun incident de perte de centrale n’est créé pendant l’essai de 24 heures ; un incident est signalé après la coupure dans le délai prévu par le ticket. (#8816)
- Envoyer un message mal formé avec un type non pris en charge. Résultat attendu : le CSR répond DUH. Consigner RSP comme non applicable tant que le support des commandes requis par le ticket lié n’est pas disponible. (#8816)

### Prérequis et moyens

- Démo ACME, plugin SIA CSR actif et simulateur PE.
- Environnement permettant les tests de protocoles, les journaux du plugin et l’observation des événements.
- Clés et valeurs de compte générées spécifiquement pour les tests ; ne pas utiliser de secrets ou d’identifiants issus d’un environnement réel.
- Disponibilité d’un poste de test pendant 24 heures pour l’essai de supervision.

Créer une fiche `À créer — Plugin CSR SIA — Conformité DC-09` dans le plan 06. Faire confirmer par décision humaine la création et l’emplacement de cette nouvelle fiche, distincte de `INT03 — Tests avec simulateur`.
