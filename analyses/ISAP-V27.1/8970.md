## 1. Étude du sujet

L'API demandait auparavant le champ `Code` du type d'incident, présent uniquement sur certains types et souvent absent des types manuels. Le ticket étend SmartShieldWebAPI afin de permettre la création d'un incident à partir de l'EntityID de l'IncidentType. Le ticket lié #8971 précise que le champ `alarm_type_eid` est transmis dans le corps du POST `/api/alarms/alarms`, que `code` reste accepté pour compatibilité ascendante mais n'est plus requis, et qu'une erreur est levée si aucun des deux identifiants n'est fourni ou résolu.

## 2. Compte rendu de la situation

**Tenants.** Les clients de l'API doivent pouvoir choisir un type d'incident par son EntityID, y compris lorsque le type ne possède pas de Code prédéfini.

**Aboutissants.** Le ticket est résolu ; le champ Code reste disponible pour les intégrations existantes, mais l'identifiant du type devient un moyen alternatif de création.

**Objectifs du test.** Vérifier qu'un POST avec `alarm_type_eid` valide crée l'incident du type choisi sans dépendre de Code, que l'ancien champ `code` reste compatible, et qu'une requête sans type reconnu est refusée.

## 3. Comparaison avec l'existant

**Recherche dans les plans.** La recherche de `#8970`, `alarm_type_eid` et « IncidentType » dans le plan 13 ne retourne aucune étape. La section « SmartShieldWebAPI » présente des contrôles de l'outil, de la connexion, des endpoints et un scénario de pièce jointe, mais ne teste pas la création d'incident par EntityID. La section « ISAP API Server : Demande de création d’alarme » utilise une autre API et ne couvre pas cet endpoint.

**Comparaison des procédures.** La section SmartShieldWebAPI du plan 13 correspond à l'API concernée. La compléter avec un scénario de création d'incident, en conservant les contrôles existants d'accès et de connexion, est préférable à la création d'une procédure indépendante.

**Issue retenue.** Issue B — Adapter l'existant : compléter la section « SmartShieldWebAPI » du plan 13 par le contrôle de création avec `alarm_type_eid` et de compatibilité avec `code`.

## 4. Procédure de test proposée

**Écarts avec la procédure existante.** Conserver les vérifications de connexion à SmartShieldWebAPI. Ajouter les requêtes de création sur un environnement isolé et contrôler l'incident créé dans la Main Courante.

**Création d'incident par EntityID**
- Préparer deux types d'incident de test dans IsapReporting : un type manuel sans Code et un type disposant d'un Code, puis relever leurs EntityID. Résultat attendu : les deux types sont présents et les identifiants relevés correspondent aux types sélectionnés. (#8970)
- S'authentifier à SmartShieldWebAPI avec un compte de test autorisé à créer des incidents. Résultat attendu : l'API accepte la connexion et le droit de création est disponible. (#8970)
- Envoyer un POST `/api/alarms/alarms` avec `alarm_type_eid` correspondant au type manuel sans Code et les champs requis par le contrat de création. Résultat attendu : la requête aboutit et retourne l'identifiant de l'incident créé. (#8970)
- Rechercher l'incident créé dans la Main Courante. Résultat attendu : l'incident existe, son type est celui correspondant à l'EntityID envoyé et ses attributs de test sont présents. (#8970)
- Envoyer une requête de création en utilisant le champ `code` pour le type qui en possède un. Résultat attendu : la compatibilité ascendante est conservée et l'incident du type correspondant est créé. (#8970)
- Envoyer une requête sans `alarm_type_eid` ni `code`, puis une requête avec un identifiant de type inconnu. Résultat attendu : l'API retourne une erreur explicite et ne crée aucun incident pour ces requêtes. (#8970)

### Prérequis et moyens

- Utiliser des types et incidents dédiés au test sur une base réinitialisable.
- Disposer du schéma à jour de l'endpoint et des paramètres obligatoires de création.
- Utiliser un compte API et des attributs de test ; ne pas reprendre d'identifiants ni de mots de passe du plan.

## 5. Intégration proposée

Dans le plan 13, compléter la section **SmartShieldWebAPI** après les contrôles de connexion à l'API, par un sous-titre **Création d'incident par EntityID du type**.
